# Kinds follow the forwarder

A resource's kind is fixed. It is the hash of the resource's logic ref and label ref, and the resource's commitment covers both. What is not fixed is the point the compliance circuit uses for that kind when it builds the delta — the kind point. The circuit takes it from the table in force when the proof is made, and uses the kind itself when the table has no entry for it. The delta check is per transaction. So assigning a kind a new kind point does not, by itself, make resources of that kind unusable: a transaction that consumes them balances as long as every resource in it uses the table in force. Two things do go wrong, and they are the only rules.

**R1 — One forwarder.** Two kinds may share one kind point only if one forwarder holds the tokens behind both. Otherwise a token deposited under one kind can be withdrawn under another. This is the rule that protects funds, and it is why sharing a kind point is reviewed like a permission to create tokens.

**R2 — Exit.** A kind with unspent resources must always have a way out: the forwarder accepts its logic ref, so its resources unwrap; or its kind point equals that of a kind the forwarder accepts, so its resources convert first. This is the rule that keeps resources usable. It breaks when the forwarder has moved to a new logic ref and the entry that let the old resources convert is gone.

So a table is a set of fungibility domains. A fungibility domain is one forwarder holding one token on one chain, and the kinds whose resources those tokens back. Every member is assigned the fungibility domain's kind point: the kind of the active circuit version under the current forwarder's label. That entry is therefore assigned its own kind, and every other member is an alias of it. The members are every listed circuit version under the current forwarder's label and, on a chain that records a V1 forwarder, the logic ref that V1 forwarder accepts under its own label. Generic call and padding have no fungibility domain: their resources are ephemeral, so nothing is ever made fungible with them. The generic call entry is assigned its own kind, which the circuit would use anyway, and padding is not listed at all, since the circuit derives the same point without a table.

Which kind point a fungibility domain uses does not matter for safety: moving a whole fungibility domain to a new one only makes in-flight transactions re-prove. So the kind point follows the active version, the one the backend creates resources of. A release makes the new version active and the previous one deprecated, which moves every ERC20 kind point on every chain to the new version's kind and turns the previous version's rows into aliases. The active version keeps its own kind under the current forwarder's label, so that it needs no table to know its kind point; the deprecated versions and the V1 members are what the table exists for. Exactly one version is active, and it is the highest listed: an older version never becomes active again, because a broken release is refused at the adapter and replaced by a higher one, and the backend can go back to creating an older version without any change to the table.

The protocol adapter, not the table, stops a broken circuit. The table can only change what a circuit's resources are fungible with, and anyone can prove with a published circuit on their own machine. A version the adapter refuses stays listed, with rows that nothing can use and that cost nothing.

## The V1 forwarder

On a chain that ran v1, the ERC20 forwarder changes once. The V1 forwarder is immutable and fixes the v1 protocol adapter as its caller, so v2 needs a forwarder at a new address, and with it a new label. The current forwarder is an upgradeable proxy, so its address and its label stay across upgrades. The V1 forwarders accept `bc1232…`, the logic ref the current forwarders accept, so a V1 resource differs from a current one only in the forwarder inside its label. The change is therefore a forwarder fact, not a circuit version. A crate release such as 2.0.0 or 3.0.0-rc.2 does not tell the two resources apart, and `data/circuit-versions.json` keeps one line per logic ref.

The forwarder repository records each V1 forwarder with the logic ref it accepts, as pa-evm records the v1 protocol adapters. The generator reads that record through the forwarder bindings. Every table of a chain that records both a V1 forwarder and a current forwarder gets V1 members, one per token the supported-token list marks for conversion. On a chain whose adapter did not take the v1 state, they are harmless: resources created on v1 reach a v2 adapter only through the state migration, so a V1 resource there can only come from a conversion inside its fungibility domain.

The V1 members enter the table before the tokens move, and the order of the migration keeps R1. The table is installed while the v2 adapter is paused, before v1 stops. The v1 state is copied in, and the adapter stays paused. The V1 balances move to the current forwarder, and only then does the adapter unpause. A paused adapter executes nothing, and the current forwarder pays out only on calls from its adapter, so no V1 resource can unwrap before its tokens have moved.

## Consequences

- `data/circuit-versions.json` is the one authored decision about circuits: the ERC20 circuit versions, each with its logic ref and its status. A release appends the new version as active and sets the previous one to deprecated; the generator requires exactly one active version, the highest listed. The generator checks every version whose crate is pinned against the logic ref that crate compiles to, so raising a pin without listing the release fails the build.
- The active version's entry under the current forwarder's label is assigned its own kind, so the circuit computes it without the table; every other member is an alias the table must carry. `anoma-rm-risc0` 2.0.0-rc.5 reads each `kind_point` from the file, so a table loaded through it carries every member of a fungibility domain (ADR-0004).
- A member's `status` describes the row, not its circuit version: `active` for the active version under the current forwarder's label, `deprecated` for every other member, V1 members included. So `status` is `active` if and only if `alias_of` is absent.
- The `token_entries_share_their_fungibility_domains_kind_point` test checks the embedded tables offline: an ERC20 or SPL token entry is assigned its fungibility domain's kind point, its `status` is `active` if and only if it has no `alias_of`, and every other entry is assigned its own kind.
- The generator requires the logic ref of each V1 forwarder to be a listed version.
- The promotion gate reads each chain's current ERC20 or SPL token forwarder and requires that the logic ref it accepts is listed. That is R2, checked on chain.
- `data/tokens.json` says per token whether the V1 label joins its fungibility domain, in `fungible_with_v1`. A token set to `false`, or missing from the list, gets no V1 member, and its V1 resources stay where they are. Where every V1 resource must have an exit, every token the V1 forwarder wrapped has to be listed and set to `true`. Nothing checks this, so review must.
- A token whose V1 balance has not moved must have no V1 member when the adapter unpauses. Its `fungible_with_v1` stays `false` until the balance moves.
- pa-evm's migration run unpauses right after the copy-in. For this order it must stop before the unpause, and a second run unpauses after the V1 balances moved.
- After the V1 balances moved, the current forwarder of that adapter is upgraded, never redeployed. A new forwarder would leave the V1 tokens behind the old label while the V1 members take the new kind point, which breaks R1 and R2.
- Nothing checks that a listed version stays listed. A deleted line is the one edit review must catch, and `CODEOWNERS` routes it to a named person.
